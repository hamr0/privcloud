# Immich backup

Piece 3 of the single-source spec unifies the scheduled Immich backup and the one-time backup into one implementation. It closes findings D3, D7 (the immich-backup.sh row), D14 and D20 (docs/archive/spec-single-source.md:275-277).

## Problem: two implementations that drifted (D14)

The scheduled script is a heredoc in `setup.sh` (written by `step_immich_backup`). The one-time path is `step_immich_backup_once` in `setup.sh` (moved there from the former `privcloud` script) (docs/archive/spec-single-source.md:281-281). They differ as follows (docs/archive/spec-single-source.md:283-288):

| | scheduled script | privcloud one-time |
|---|---|---|
| layout | `$BACKUP_DIR/immich/photos`, `$BACKUP_DIR/immich/db/` | `<dest>/privcloud-backup/photos`, dump `immich-db-*.sql.gz` at the top |
| excludes | `/backups/`, `/thumbs/`, `/encoded-video/` | none |
| mirror | never `--delete` | `rsync --delete` on request, no source guard |
| retention | `find -mtime +N -delete` | none |

- The differences are accidental. The excludes were added to the scheduled script in v0.9.12 after the shared drive filled ("No space left on device"), and only `setup.sh` received them (docs/archive/spec-single-source.md:290-290).
- The one-time mirror never received the `_mirror_guard` added to the federver copies (docs/archive/spec-single-source.md:290-290).
- Real failure: the full-drive incident recurs whenever the one-time backup is used (docs/archive/spec-single-source.md:291-291).
- Code-proven failure: running both on one drive writes the library twice, under `privcloud-backup/photos` and `privcloud-backup/immich/photos` (docs/archive/spec-single-source.md:291-291).
- Mirror with an empty or unmounted `$upload_loc` deletes the destination copy, the hazard `_mirror_guard` exists to prevent (docs/archive/spec-single-source.md:291-291).

## Problem: template and sed placeholders (D3)

- The script is a heredoc with `sudo sed -i "s|__BACKUP_DIR__|..."` applied afterwards. `_configured_backup_dir` reads `BACKUP_DIR=` back from the installed script with sed, and Status parses the log text the script emits (docs/archive/spec-single-source.md:295-295).
- The better pattern already exists: `_disk_check_script` is a generator that passes values through `printf %q`, dry-runs before install and is regenerated on every reinstall (docs/archive/spec-single-source.md:295-295).
- This is not like D1: Set up rewrites the whole file each time, so nothing patches an old copy (docs/archive/spec-single-source.md:296-296).
- Unverified hazard: a `BACKUP_DIR` containing `|`, `&` or `\` is mangled by the sed delimiter. The installed script doubles as a data store (docs/archive/spec-single-source.md:296-296).

## Problem: baked values (D7)

- `immich-backup.sh` bakes in BACKUP_DIR, UPLOAD_LOCATION and RETENTION_DAYS. The live source for UPLOAD_LOCATION is `.env`, changed by `_storage_change_immich` and `step_immich_config`. Neither refreshes the script (docs/archive/spec-single-source.md:300-300).
- Other baked-value rows in the report (wrappers, Syncthing mounts with a "Reapply paths" menu, disk-check, sync job scripts) are low risk or intentional. Job scripts belong to piece 2 (docs/archive/spec-single-source.md:301-301).
- Failure (code-proven, not verified live): after moving storage, the scheduled backup keeps the old `UPLOAD_LOCATION`. A deleted old path gives a visible rc=1. If the old tree still exists, it backs up stale data and reports "Backup complete" (docs/archive/spec-single-source.md:302-302).

## Problem: cron reads and the legacy pattern (D20)

- `_cron_get/_cron_set/_cron_drop` exist, but several places still read crontab raw (`sudo -n crontab -l`, `sudo crontab -l`, `crontab -l 2>/dev/null || ...`). One site is a deliberate marker read through `_server_sudo_run` (docs/archive/spec-single-source.md:306-306).
- Raw reads cannot tell "read failed" from "empty"; `_cron_get` was fixed to distinguish them (docs/archive/spec-single-source.md:307-307).
- Set up teardown matches a narrow pattern (`immich-backup`), while Status and Remove use a 3-term pattern. v0.9.17 widened Remove only, which is drift (docs/archive/spec-single-source.md:306-307).
- Unverified failure: a legacy root cron line running `immich-db` without `immich-backup` is shown by Status and removed by Remove, but left when Set up installs the timer, so both run (docs/archive/spec-single-source.md:308-308).

## Design

- **One implementation.** `immich-backup.sh` is generated by `_immich_backup_script` (values via `%q`, dry-run, regenerated on reinstall). It accepts `--once --dest D --scope photos|db|both --mirror`. `cmd_backup_once` asks the questions and calls it via `sudo`, so layout, excludes and the mirror guard live in one place. The mirror source guard uses `_drive_verdict` / `_mirror_gate` from piece 1 (docs/archive/spec-single-source.md:312-312).
- **Run-time `.env`.** The script reads `UPLOAD_LOCATION` from the repo `.env` at each run, as disk-check does. Only BACKUP_DIR and RETENTION live in a small `/etc/immich-backup.conf`, which replaces the sed read-back. `_configured_backup_dir` reads it, and the repo path comes from the install step, not a hardcoded value (docs/archive/spec-single-source.md:313-313).
- **One layout for both modes.** One-time now writes to `<dest>/immich/...` to match the scheduled layout, so the library is never written twice. This is listed in the CHANGELOG as a behaviour change (docs/archive/spec-single-source.md:314-314).
- **One cron helper.** A single `_immich_cron_lines` with one pattern constant, and `_cron_get` everywhere, so Status can show "unknown" on rc=1 (docs/archive/spec-single-source.md:315-315).
- **One schedule by design.** There is exactly one Immich backup schedule, so Remove and Status never need a chooser. The user-versus-system unit differences between the Immich units and sync-job timers are not merged (docs/archive/spec-single-source.md:316-316).

## Tests

- **Pin first.** sync-mirror.sh already asserts the scheduled path stays append-only. Add pinning for the generated script (excludes, layout, retention, `--once` flags) and for `cmd_backup_once` argument building, neither of which has tests today (docs/archive/spec-single-source.md:320-320).
- **Fail-first.** Remove an exclude or drop the guard in the new generator and confirm the test fails (docs/archive/spec-single-source.md:321-321).
- **New tests** (docs/archive/spec-single-source.md:322-322):
  - `BACKUP_DIR` containing `|`, `&`, `\` round-trips.
  - `UPLOAD_LOCATION` changed in `.env` is used on the next run without regenerating.
  - A one-time mirror with an empty source is refused.
  - A legacy `immich-db` cron line is handled identically by Set up, Status and Remove.
- **Known gaps.** No test covers `cmd_backup_once`, `cmd_config`, `_storage_change_immich`, the generated `immich-backup.sh`, or the real `_cron_*` functions (suites stub them; disk-check.sh re-defines them) (docs/archive/spec-single-source.md:323-323).
- **Size and risk.** Size M, risk medium: a broken backup script fails silently until the next run. A live run of the scheduled job and one one-time run are required before merge (docs/archive/spec-single-source.md:324-324).

## Acceptance

- One script produces both modes, and the privcloud one-time path has the same excludes and layout (docs/archive/spec-single-source.md:326-326).
- Mirror without a valid source is refused (docs/archive/spec-single-source.md:327-327).
- Changing Immich storage needs no script refresh (docs/archive/spec-single-source.md:328-328).
- Set up, Status and Remove use one legacy-cron pattern and `_cron_get` (docs/archive/spec-single-source.md:329-329).
